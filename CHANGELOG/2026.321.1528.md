# 2026.321.1528 — feat(doctor): report NVIDIA CDI injection health — spec, mounts and driver-version match

## Summary

`charly doctor` gains a group, **NVIDIA CDI (GPU device injection)**, with three checks. It exists
because a GPU container that resolves the *wrong* driver userspace fails in a way nothing else in the
toolchain reports: the deployment looks healthy, the API answers, and inference silently runs on CPU.

Three checks, each of which must hold for `--device nvidia.com/gpu=all` to mean anything:

1. **NVIDIA container toolkit** — `nvidia-ctk` / `nvidia-container-toolkit` / `nvidia-cdi-hook` on
   PATH. It is HOST tooling (it generates the spec); without it no spec can be produced or refreshed.
2. **CDI spec** — a spec in `/etc/cdi` or `/var/run/cdi`, parsed, with the **device, mount and
   driver-library counts** reported. A spec with devices but **zero mounts** is the failure mode this
   check was built for: containers then get device nodes only, and every `libnvidia-*`/`libcuda` they
   resolve comes from their own image.
3. **CDI driver version** — the version of the HOST's own driver user-space (the files the injection
   carries, read from `libnvidia-ml.so.<version>` in `/usr/lib`, `/usr/lib64` or the Debian multiarch
   directory), compared against `/proc/driver/nvidia/version`.
   The kernel module is host-global, so the userspace the injection delivers must equal it; a
   half-upgraded host therefore produces a mismatch that every GPU container inherits.

**Measured on the machine that motivated this — and corrected mid-review.** Both
`/etc/cdi/nvidia.yaml` and `/var/run/cdi/nvidia.yaml` declare three devices and **zero** mounts, so the
spec alone supplies no driver library; but the toolkit's runtime hook does, so the group reports the
mechanism rather than a verdict based on the spec's mounts:

```
$ charly doctor
[OK] NVIDIA CDI (GPU device injection)
  [+] NVIDIA container toolkit -- /usr/bin/nvidia-ctk
  [+] CDI spec -- /etc/cdi/nvidia.yaml: kind=nvidia.com/gpu, 3 device(s), 0 mounts — the driver comes
      from the toolkit's runtime hook (/etc/nvidia-container-runtime/config.toml), not from the spec;
      a spec-only consumer would get device nodes only
  [+] CDI driver version -- host userspace 615.78.08 == running kernel module 615.78.08
```

The evidence for that correction is the decisive experiment, on a GPU image whose driver user-space
had been stripped:

```
$ podman run --rm --device nvidia.com/gpu=all ghcr.io/opencharly/nvidia:2026.321.1448
615.78.08, NVIDIA GeForce RTX 4080 SUPER
/usr/lib/libnvidia-ml.so.1 -> libnvidia-ml.so.615.78.08          # the INJECTED host library
NVRM version: NVIDIA UNIX Open Kernel Module for x86_64  615.78.08
```

So: the stripped image + the injection = the host's own driver, correct version, `nvidia-smi`
working. What breaks a GPU container is the opposite shape — an image that ships its own driver
user-space, which then wins the SONAME resolution against the injected files. That is
opencharly/layer-cuda#21, and its image-side fix is opencharly/layer-cuda#22; this group is the host-side
half (mechanism + version pair), and the container-side half is the candy/bed probe.

## How tested

**1. Unit tests, including both directions of the shape that matters** (`cdi_test.go`):

```
$ GOWORK=off go test -count=1 ./...
ok  	github.com/opencharly/plugin-doctor/candy/plugin-doctor	0.055s
```

The fixtures are the two measured shapes: a spec with three mounts (one device, two driver libraries)
and the broken one that declares devices with `containerEdits: {}`. The test forces the runtime-hook
seam BOTH ways and asserts the verdict in each: **hook absent + 0 mounts ⇒ `CheckWarning`**, with the
detail naming the mechanism; **hook present + 0 mounts ⇒ `CheckOK`**, with the detail naming the hook.
It also asserts that a host userspace/module skew (`620.70.06` vs `615.78.08`) warns **naming both
versions**, that the healthy pair is `CheckOK`, that a missing spec reports not-found rather than
"healthy", and that a SONAME-only name (`libnvidia-ml.so.1`) yields no version rather than inventing
`1` — comparing against nothing is how this check would rot.
