# 2026.243.1554 — feat(doctor): detect a stranded aardvark-dns, which kills container DNS silently

## Summary

`charly doctor` cannot see the single most confusing container-networking failure on a rootless
host: **a stranded `aardvark-dns`**.

podman tears down the rootless network namespace when the container count reaches zero, and
creates a fresh one on the next start. `aardvark-dns` is not restarted with it — the process
keeps serving inside the namespace nothing uses any more, so `10.89.0.1:53` has **no listener**
where containers actually query.

Nothing looks wrong:

- the process is alive (`pgrep aardvark-dns` finds it)
- the bridge is up in the new namespace with the correct gateway (`podman1  10.89.0.1/24`)
- the zone file is correct and **current** — it even lists the new containers by name and IP
- `podman network inspect` reports `dns_enabled=true`

Every `getent hosts <peer>` inside every container just returns empty, and the symptom appears
far from the cause as `cannot resolve <name>` in whatever runs next.

**A disposable bed triggers this routinely**: its teardown removes the last containers on an
otherwise idle host. The failure therefore shows up *after* a green run, in the *next* run —
which is what makes it so misleading. The obvious suspects are the change under test and the
bed that just passed, and neither is at fault.

## What this is, in the field

A two-member fleet bed paired correctly at 13:00 (`paired 10.89.0.135:9777`). Every run after
that failed at the same step with `cannot resolve <peer>`. The cause:

```
aardvark-dns           net:[4026534654]      <- still serving here
podman rootless netns  net:[4026533620]      <- everything actually lives here
```

Cross-container resolution was dead **host-wide** — including other sessions' beds on the same
host, not only the one being debugged. Hours went into the change under test, the bed's mount
configuration, and podman's overlay store before the namespaces were compared.

`charly doctor` reported everything OK throughout, because it checks that binaries exist.

## The check

Compares aardvark's network namespace with the one podman currently uses:

```
Podman Machine
  aardvark-dns namespace   STRANDED: aardvark pid 1906277 serves net:[4026534654]
                           but podman uses net:[4026533620] — container-name DNS is
                           dead for every container
                           hint: kill -9 1906277 && rm -f ${XDG_RUNTIME_DIR}/containers/
                                 networks/aardvark-dns/aardvark.pid && podman network reload --all
```

The hint includes removing the stale pidfile deliberately: killing the process alone leaves
podman believing a healthy daemon is already running, so it does not start a replacement. That
was learned the hard way — `SIGTERM` is also ignored by the stranded process, hence `-9`.

## How tested

```
$ go build ./... && go vet ./... && go test ./...
ok  	github.com/opencharly/plugin-doctor/candy/plugin-doctor	0.006s
```

**Four guards**, each pinning something the failure taught:

- a stranded daemon is reported `CheckMissing`, naming **both** namespaces so the operator can
  see the mismatch rather than take it on trust
- the hint is actionable — it must mention the kill, the **pidfile**, and the reload
- matching namespaces stay quiet, so the check does not become noise operators learn to ignore
- a not-running daemon is **OK** (podman starts it on demand; flagging an idle host would be a
  false alarm), and an unavailable comparison invents no verdict in either direction

**Negative control** — the check reduced to the presence-only behaviour it replaces:

```
--- FAIL: TestAardvarkStrandedIsReportedMissing
FAIL	github.com/opencharly/plugin-doctor/candy/plugin-doctor
```

The decision is split into a pure `aardvarkVerdict(pid, got, want)` so the stranded case is
exercised **without** reproducing it on a live host — reproducing it means breaking DNS for
every container on that host, including other people's work.

**Verified against the real machine** after remediation, confirming the logic reads the true
state rather than only synthetic inputs:

```
pid=2451338 got=net:[4026533620] want=net:[4026533620] match=true   -> OK
```

Before remediation the same probe read `got=net:[4026534654] want=net:[4026533620]`, which is
the STRANDED branch.

`aardvarkPID` scans `/proc` rather than shelling out to `pgrep -f`, whose pattern form also
matches the caller's own command line — a real hazard when the caller is itself a shell.
